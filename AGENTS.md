# AGENTS.md — MedApp Android

## Назначение

Android-клиент для учёта физических упаковок лекарств, аптечек и заданных человеком
курсов приёма. Приложение не назначает лечение и не определяет взаимозаменяемость.
Подробный продуктовый и технический контракт — в [PLAN.md](PLAN.md).
Наличие компонента в плане не означает, что он реализован: проверяйте код и матрицу J4.

## Инварианты

- Каждая физическая упаковка учитывается отдельно. Покупка другой пачки не пополняет старую.
- Курс, источник, приём и серверная бронь различаются (PLAN C0, D5–D6).
  Нехватка меняет обеспечение, а не расписание.
- Плановая доза берётся из одной упаковки. Активное назначение упаковки уникально;
  черновик её не занимает. Доза-подсказка упаковки независима от дозы курса.
- Доза и расписание активного курса неизменны. Изменение лечения — отмена старого курса
  с сохранением истории и создание нового; источники и выделения можно изменять (PLAN D5).
- Приёмы и очередь не удаляются каскадом. Пропуск, неответ и закрытие уведомления не списывают запас.
- Снимок сервера не перезаписывает пользовательские локальные сведения (PLAN E4, F5).
  Подтверждённый остаток и ожидающие операции учитываются без повторного расхода (PLAN E1–E3).
- Подготовленный изменяющий запрос неизменен. Не повторяйте неустановленный расход
  со свежим предусловием; действуйте по политике операции из PLAN E3. Принятую там
  эвристику большего остатка сохраняйте; редкое исключение записано как RK-SYNC-01.
- `ui → domain ← data`; домен независим от Android/Room/Ktor, время получает через `Clock`.
  DTO, Entity и доменные модели не смешиваются; ViewModel не обращается к HTTP и DAO.
  Сохранённые данные экран наблюдает из Room; несохранённый ввод остаётся состоянием формы.
- Учётные данные не попадают в логи, навигацию, отчёты об ошибках и резервные копии (PLAN G).

## Порядок работы

1. Проверьте состояние репозитория и существующую реализацию; сохраняйте чужие изменения.
2. Прочитайте разделы под задачу. Не добавляйте сущности и таблицы без обоснования.
3. Выполните изменение и соответствующие проверки. Укажите, что проверено и что не запускалось.
4. Обновите затронутые решения и статус в PLAN. AGENTS меняйте только при изменении рабочих правил.

## Проверки

Из корня клиента:

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:connectedDebugAndroidTest
./gradlew :app:lintDebug :app:assembleDebug
```

Инструментальные тесты требуют эмулятора или устройства. Набор тестов зависит от реализованных PR.
`WireContractTest` и клиентский `ContractProbe` запланированы в PR 5;
их наличие и команду запуска проверяйте по коду, не выдавайте запланированное за выполненное.
Запуск сервера и фактические проверки HTTP описаны в PLAN B7/J1.

## Границы изменений

- Проблемы серверного контракта описывайте с воспроизведением; не меняйте серверный API молча
  в рамках задачи клиента. Следуйте уже согласованному пользователем объёму работы.
- [HomeMedkit-App](https://github.com/pewaru-333/HomeMedkit-App) — референс подходов и
  недокументированного CRPT API. Копировать его код, ресурсы и тексты запрещено.
- Если задача включает коммиты, сообщения передавайте через файл: `git commit -F <file>`.
